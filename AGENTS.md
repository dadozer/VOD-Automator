# VOD Automator Architecture Rules & Persistent Instructions

## 1. VOD vs. Live Chunk Separation
- **Never mix or interleave VOD and Live chunks**: Live segments (`seq_*.ts`) and VOD backfill segments (`vod_seq_*.ts`) have incompatible timestamps, discontinuity sequences, and chunk boundaries. They must NEVER be combined or sorted together into the same video output.
- **Standalone VOD Backfill Stitching**: When a VOD backfill finishes downloading (either Full VOD or Current Game), immediately stitch those `vod_seq_*.ts` chunks into their own separate video file (`type: 'vod'`).
- **Independent Live Lifecycle**: Live segments (`seq_*.ts`) belong exclusively to the active live session and must only be stitched separately when a live game change occurs or when the broadcast concludes (`type: 'live'`).
- **Cleanup**: Delete temporary VOD chunks once their standalone VOD video is successfully compiled and verified. Obsolete live chunks are pruned after each live game segment is verified.

## 2. Versioning & UI Sync Rules
- Increment the small/third version number (e.g. 4.4.1 -> 4.4.2) when any changes are made.
- Suggest incrementing the "middle" or "large" version number when a more significant change is made.
- Ensure the version number is synchronized across `package.json` and the visible badge at the top left of the UI dashboard (`src/App.tsx`).

## 3. Approval Rule
- Always ask for approval to make code changes if the prompt did not specifically ask to make a change or update.

## 4. Production Service & Build Invariant
- **Bundled Service Execution**: Windows background services must execute the bundled, self-contained `dist/server.js` with an explicit `workingDirectory: projectRoot`.
- **No Runtime Loaders in Service**: Never point the background service wrapper (`node-windows`) to raw TypeScript (`server.ts`) or rely on runtime loaders (e.g., `--import tsx`) inside Windows Service Control Manager.
- **Dynamic Root Anchor & Storage Permissions**: Server paths for configuration (`config.json`), logs (`system.log`), state (`state.json`), static assets (`dist/`), and default video output (`downloads/`) must be dynamically anchored to `PROJECT_ROOT` to prevent Windows Service permission failures (`EPERM` at drive root). Legacy relative paths (e.g. `../../downloads`) must self-heal to `PROJECT_ROOT/downloads`.
- **Global Crash Guards**: `server.ts` must maintain active `uncaughtException` and `unhandledRejection` guards to log unexpected runtime errors to `system.log` without abruptly terminating the process or taking down the local web dashboard.

## 5. Live Stream Recovery & Disk Invariants
- **Guaranteed Folder Existence**: Active session restored from `state.json` or new stream initializations must ensure `session.folderPath` exists recursively (`mkdir -p`) before any segment writing to prevent `ENOENT` crashes.
- **Live Edge Lock-On (Gap Capping)**: Live playlist recovery is capped to the active playlist window (max 30 chunks / ~60s). Gaps larger than 30 chunks (caused by app restarts, sleep, or network downtime) must immediately advance `highestSeq` to lock onto the live edge. Expired segments must never be requested from the live playlist; they are handled via VOD backfill.
- **Deleted Folder Session Flush**: If a stream's `folderPath` is deleted on disk by the user, the application must immediately flush and discard any persisted session state for that channel, ensuring a fresh session initialization and re-triggering the backfill prompt.

## 6. VOD Backfill & Chat Timeline Synchronization Invariants
- **Broadcast Start Anchor**: `videoStartTimeMs` must always anchor to the broadcast's actual creation time (`streamCreatedAtMs`), ensuring `awaitsUserChoice` buffers live messages properly when joining mid-stream.
- **Paired Chat Generation for VOD**: Whenever a standalone VOD backfill is stitched (`type: 'vod'`), a paired JSON chat file (`[game]_vod_backfill_[date].json`) must be produced alongside the `.mp4`, with comment offsets normalized to `0s` at the start of the VOD clip.
- **Live Chunk Chat Offsets**: Live video chat slicing (initial game, subsequent games, custom clips, and extensions) must never use naive `firstChunkInVideo * 2` or raw `firstChunkInVideo * avgChunkDur` from sequence `0`. Offsets must anchor to real broadcast presentation time (`(game.startTimeMs - session.videoStartTimeMs) / 1000` or `session.initialJoinOffsetSec`) adjusted by `(firstChunkInVideo - referenceChunk) * avgChunkDur` using the probed container duration (see Section 9).
- **Backfill Chat Slicing Coordination**: Standalone VOD stitching (`stitchVideoChunks` with `type: 'vod'`) must await the completion of in-flight VOD chat backfill pagination (`activeChatBackfillPromise`) before reading and slicing the chat file, preventing premature partial-chat generation.
- **VOD Chat Slicing Window**: When generating paired chat for standalone VOD backfills, `vodEndOffsetSec` must encompass all backfilled messages up to the live stream join offset, and `repairChatJsonFile` must validate and seal the master chat file before slicing to guarantee zero dropped or truncated comments.
- **Immediate Standalone VOD Chat Construction**: Standalone VOD backfill chat files (`[game]_vod_backfill_[date].json`) must be assembled and written directly from the in-memory backfill dataset upon VOD chat download completion, ensuring zero truncation and instant availability when video remuxing finishes.

## 7. TwitchDownloader CLI Header & Schema Parity
- **TwitchDownloader CLI Header & Schema Parity**: All standalone and sliced chat JSON files (`vod_backfill`, game splits, and repair routines) must adhere to TwitchDownloader's C# deserializer schema. Specifically, `streamer.id` must strictly be a 32-bit integer (never an empty string `""` or null), `FileInfo` must include version metadata (`1.5.3`), and third-party emotes must reside under `embeddedData.thirdParty` to prevent `System.Text.Json` deserialization failures during CLI rendering.
- **Pre-Flight Render Sanitization**: Any chat JSON file passed to `TwitchDownloaderCLI` for rendering must pass through pre-flight validation (`sanitizeChatJsonForRendering` / `repairChatJsonFile`) to normalize non-numeric `streamer.id` values, populate `FileInfo`, and ensure valid `embeddedData` before invoking the CLI process.

## 8. Game Slicing Buffer Preservation Invariants
- **Buffer Preservation on Override / Manual Splice**: When a buffer override ("Skip Buffer") or manual cut is triggered, the preceding game segment's ending chunk boundary (`endIdx`) must never truncate back to `nextGame.startChunk`. It must evaluate to `Math.min(activeChunkList[last], nextGame.startChunk + CHUNK_BUFFER)` so all chunks recorded up to the moment the action was triggered are retained in the first video, while the subsequent segment maintains its leading buffer (`nextGame.startChunk - CHUNK_BUFFER`).

## 9. Non-Fixed Chunk Length & Duration Determination Invariants
- **Never Assume Fixed Chunk Length**: Live HLS chunks from Twitch (`seq_*.ts`) and VOD chunks (`vod_seq_*.ts`) are NEVER guaranteed to be exactly 2.000 seconds. Broadcaster frame rates (e.g. 59.94 vs 60 fps), encoder keyframe intervals, and audio packet pacing cause real chunks to vary (often ~1.995s). Never calculate video duration, slice boundaries, or chat start offsets using naive `chunkCount * 2` or `chunkIndex * 2`.
- **True Container Duration via Media Probing**: After stitching video chunks into an output `.mp4`, always probe the true container duration via `getVideoDurationSeconds` (using `ffprobe` format/stream duration with `ffmpeg -i` fallback) before generating paired chat slices or invoking `TwitchDownloaderCLI chatrender`.
- **Chat Render Parity with `--ending`**: Always supply the exact probed container duration to `TwitchDownloaderCLI chatrender` via `-e / --ending <duration>s` and set `video.length` and `video.end` in the paired chat JSON to this exact probed value to guarantee perfect length alignment between rendered chat and video.
- **Accurate Chat Slicing Start Offsets**: Slicing boundaries must anchor to real stream presentation time / broadcast start timestamps (`(game.startTimeMs - session.videoStartTimeMs) / 1000` adjusted by buffer chunk durations) rather than multiplying sequence numbers by 2, preventing multi-hour cumulative drift from distorting subsequent game segments.
- **Clock Drift Compensation for Long Broadcasts**: For extended subathons / long broadcasts (10+ hours), provide intelligent linear drift compensation between UTC IRC wall-clock time and physical hardware media presentation time (PTS) based on container duration vs. wall-clock chat span.

## 10. Enhanced Broadcasting & Usher Source Playlist Selection Invariants
- **Never Fallback to `playlists[0]`**: On Twitch Enhanced Broadcasting (multi-encode CMAF/fMP4), variants are labeled by resolution (`1440p60`, `1080p60`, `720p60`, `480p30`, `360p30`, `160p30`) rather than `VIDEO="chunked"`, and live Usher edge servers return them in non-deterministic order. Always sort non-audio playlists by descending pixel area (`width * height`), source tag (`chunked`/`source`), frame rate (`FRAME-RATE`), and bitrate (`BANDWIDTH`), selecting the highest quality tier.
- **Explicit Codec Advertisement on Usher**: All Live and VOD Usher master playlist requests must include `&supported_codecs=av1,h265,h264&platform=web` alongside `&allow_source=true` so HEVC (`h265`) 1440p60 tracks are always exposed when available.
- **CloudFront VOD `chunked` (1440p60 HEVC) Upgrade**: When `PlaybackAccessToken` is unauthenticated (`maximum_resolution: "FULL_HD"`), Usher strips `chunked` (1440p60 HEVC) from the VOD master manifest and caps the list at `1080p60`. On VOD playlist resolution (`isLive: false`), automatically probe `/chunked/index-dvr.m3u8` on the same CloudFront base path and upgrade to the 1440p60 HEVC track when HTTP 200 is returned.
- **Graceful OAuth 401 Fallback & Live Refresh**: If Twitch GQL rejects a configured `browserOAuthToken` with HTTP 401/403, `postTwitchGql` must log a warning and retry unauthenticated so monitoring and recording never stall. Updating `browserOAuthToken` or `browserClientId` in Settings must immediately trigger `refreshMediaPlaylist` for all active recording sessions.
- **Strict `init.mp4` (Live) vs. `vod_init.mp4` (VOD) Isolation**: Every CMAF resolution tier has its own `stsd` codec (`hev1` vs `avc1`) and pixel resolution in its initialization segment. Live streams must save to `init.mp4` and VOD backfills must save to `vod_init.mp4` so a live stream and a VOD backfill in the same session folder never overwrite or mismatch each other's initialization headers. In `resolveInitSegment`, always query Twitch CDN for the active broadcast before falling back to sister folders.
- **Opaque Live Segment URL Guard**: Enhanced Broadcasting live playlists use opaque per-segment token URLs (`.../v1/segment/CpYD...mp4?dna=...`) that do not contain sequence numbers. Missing-segment recovery in `pollPlaylist` must verify that regex sequence-number substitution actually modifies the URI before fetching, preventing duplicate downloads of `segments[0]` under fake sequence numbers.
- **Variable VOD Segment Duration (`10.0s` CMAF VODs)**: Enhanced Broadcasting VODs use `10.000s` CMAF segments (`0.mp4`, `1.mp4`) rather than `2.000s` segments. Always compute average VOD segment duration (`avgVodSegDur`) from the parsed VOD manifest rather than assuming 2 seconds per VOD chunk.
